# Project Zomboid B42.20 Compatibility Instructions

Use this guide for B42.20 migration, compatibility, live-install, mod-list,
asset, Java-agent, and log-error work in this workspace. Keep
`b42.19-codex-instructions.md` as the B42.19 reference.

## Build Isolation

- The protected B42.19 game is
  `/home/cjstorrs/games/Project Zomboid Linux 42.19.0`.
- The protected B42.19 user-data tree is `/home/cjstorrs/Zomboid`.
- The B42.20 game is
  `/home/cjstorrs/games/Project Zomboid Linux 42.20.0`.
- The B42.20 user-data tree is
  `/home/cjstorrs/games/Project Zomboid Linux 42.20.0/user-data/Zomboid`.
- Never fix B42.20 by editing, removing, relinking, or refreshing a B42.19
  game or user-data file.
- Before and after a B42.20 change, verify the affected B42.19 mod payload and
  load-list entries remain unchanged. Preserve the known B42.19 game-tree
  fingerprint when it is available.

## Version-Specific Mod Changes

- Put B42.20-only metadata, Lua, scripts, Java, or assets under `42.20/`.
- Preserve the existing `42/`, `42.12/`, `42.13/`, `42.15/`, `42.19/`, and
  lowercase `common/` payloads used by older builds.
- A `42.20/` descriptor must keep the stable `id=` and dependency IDs unless a
  deliberate save-breaking migration was approved.
- When only part of an older version payload changes, begin from the complete
  active predecessor version and apply the narrow B42.20 change. Do not create
  a partial version folder that accidentally hides required predecessor files.
- For a non-project-backed third-party mod, keep the B42.20 repair inside the
  isolated B42.20 copy. Prefer a current verified Workshop payload when
  upstream already fixed the problem.
- Reserve `CJS Tweaks` names for separate mods that modify another mod.
  `cjsLinuxPathCompat` is an independent compatibility mod and must not be
  described or packaged as a tweaks mod.

## GOG Launcher And ZombieBuddy

- The B42.20 launcher passes
  `-javaagent:ZombieBuddy.jar -- "-cachedir=${GAMEDIR}"` to
  `ProjectZomboid64`.
- `ZombieBuddy.jar` belongs in the B42.20
  `game/projectzomboid/` directory. Do not reuse the B42.19 game directory at
  runtime.
- The current verified agent is ZombieBuddy 2.3.2 with SHA-256
  `6dd95cedce60f03bf8b8cefd0d19eb156230e0d54bffa07de9da5212a06c7be6`.
- The B42.20 `ProjectZomboid64.json` max heap is deliberately raised from the
  stock `-Xmx3072m` to `-Xmx12g`, matching B42.19. Preserve B42.20's
  `--enable-native-access=ALL-UNNAMED`,
  `--add-exports=java.base/jdk.internal.misc=ALL-UNNAMED`, and
  `-Djava.library.path=natives/` arguments; do not replace the complete file
  with the older B42.19 JSON.
- A GOG update may overwrite both the launcher and `ProjectZomboid64.json`.
  Reapply the isolated cachedir, ZombieBuddy agent, and 12 GB heap settings
  after verifying the updated files.

## B42.20 Tile-Definition Validation

B42.20 rejects tile-definition data that B42.19 accepted:

- `tiledef=` file numbers must be from `100` through `8189`.
- A binary `.tiles` file must start with the four-byte magic `tdef`.
- A `.tiles` file may contain at most `512` tilesets.
- Each tileset may contain at most `512` tiles.

Treat `IsoWorld.LoadTileDefinitions` errors as load-blocking. Check current
Workshop sources before patching. Do not merely suppress the exception: update
the actual tile payload or use an upstream B42.20 build whose compiled
texture-pack and tile-definition data agree.

Confirmed official B42.20 remaps:

- Raccoon City: `shisantiles 9527` -> `shisantiles 2527`.
- BuildingCraft: `BuildingCraft 9528` -> `BuildingCraft 2528`.

Confirmed dependency handling:

- Use the current official Melos Tiles payload. It splits the old 790-sheet
  definition into tiledefs `237` and `238`, with 493 and 297 sheets.
- Neat Building has a complete `42.20/` payload. Its legacy zero-magic
  `NeatBuilding_Tiles.tiles` is converted to `tdef`, and
  `NB_building_tiles_01` is explicitly sheet number `1`.
- Erika's Tiles has a B42.20-only compatibility tiledef. B42.20 allocates only
  512 sprite IDs per sheet, so `walls_exterior_detailing_erika_01` is reduced
  from 560 to 512 entries and `walls_interior_detailing_erika_01` from 576 to
  512. The unrepresentable trailing 48 and 64 sprites are unavailable in
  B42.20; raising the engine limit would cause sprite-ID collisions.
- Use `.tools/pz-b4220-tiledef-convert.py` for these narrow conversions and
  validate every output by parsing the entire binary with no trailing data.

## Linux Script-Path Java Patch

B42.20 still lowercases the path returned by
`ZomboidFileSystem.getRelativeFile()` inside
`ScriptManager.searchFolders(URI, File, ArrayList)`. On Linux, a failed
symlink-aware relativization can therefore become a bogus lowercased absolute
path beneath the active `mods/` directory.

- Do not create filesystem path shims for this bug.
- Use the independent B42.20-only `cjsLinuxPathCompat` ZombieBuddy mod. Its
  `42.20/` Java patch intercepts non-directory calls to
  `ScriptManager.searchFolders`, reproduces the vanilla `.txt` filter, and
  adds the relative path without lowercasing it.
- Keep the B42.19 direct `projectzomboid.jar` patch and any historical B42.19
  compatibility paths untouched.
- Do not modify the B42.20 `projectzomboid.jar` while the ZombieBuddy patch is
  viable. A direct native JAR patch is only a backed-up fallback if a later
  build can no longer be hooked safely.
- Treat copied `mods/home/...` trees as stale B42.19 compatibility artifacts.
  They are not part of the B42.20 fix and must never point B42.20 at
  `/home/cjstorrs/Zomboid/mods`.
- After each game update, inspect the 42.20
  `ScriptManager.searchFolders(URI, File, ArrayList)` bytecode and rerun the
  patch tests before enabling the mod.

## B42.20 File-Writer Restriction

B42.20 restricts `getFileWriter()` to `ini`, `cfg`, `txt`, and `log`
extensions. It also retains the argument order
`getFileWriter(filename, createIfNull, append)`.

- Daily Report Journal uses a complete `42.20/` payload with `journal.txt`,
  `xplog.txt`, `.keep.txt`, and `.txt` migration backups.
- Its writer calls must pass `true` for `createIfNull` and the requested append
  state as the third argument.
- The isolated B42.20 user-data copy retains every legacy `.djr` file and has
  content-identical `.txt` copies. Never rename or remove the B42.19 originals.

## B42.20 Lua And Object-Sync Changes

- B42.20 removes `IsoObject.transmitCompleteItemToServer()`. Do not replace it
  with a dynamic method guard: the method is absent from the B42.20 Java API.
- For a locally created single-player object, add it to its square normally.
  Server-side creation may call `transmitCompleteItemToClients()` after
  `AddTileObject()`. A multiplayer client must use a server-authoritative
  command path rather than constructing and transmitting a complete object.
- ChairBarricade has a complete `42.20/` payload. It places the chair object
  successfully before consuming the inventory chair, locking the door, or
  multiplying door health, preventing the old partial-failure state.

## Native B42.20 Diagnostics Patches

The following vetted helpers have been applied only to the B42.20
`projectzomboid.jar`:

- `install-imported-skeleton-missing-body-log-patch.sh`
- `install-map-metadata-validation-log-patch.sh`
- `install-vanilla-fluid-container-name-patch.sh`
- `install-vanilla-muldraugh-mannequin-zone-patch.sh`
- `install-vanilla-piano-uiconfig-patch.sh`

The map-metadata helper includes the non-fatal B42.20 basement merge duplicate
room/building metadata validation emission. It changes the diagnostic level;
it does not alter `map_basements.bin`, map cells, rooms, or the save.

Every helper creates a B42.20-local backup. GOG updates replace the JAR, so
rerun each helper in dry-run mode against the new build and apply it only when
its exact guarded bytecode match still succeeds. These patches are separate
from the ScriptManager Linux path correction, which remains a ZombieBuddy
patch and must not be applied directly to the B42.20 JAR.

## Log Review

- Use the isolated B42.20 `console.txt` as the source of truth.
- Group repeated messages by the earliest explicit exception. A later
  `WorldDictionaryException` or `GameLoadingState` failure is usually a
  downstream result of an earlier script or tile-definition error.
- Do not count repeated building/room ID diagnostics as independent root
  causes until map-token shadowing, cell overlaps, duplicate map payloads, and
  tile-definition failures have been resolved.
- Preserve the previous console log before each validation launch so fixed and
  current sessions cannot be confused.
